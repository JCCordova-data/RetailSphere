# RS-032: integration testing results

## Objective and scope

Document the verified integration results for the five RetailSphere dbt models:
`orders`, `customers`, `order_items`, `products`, and `monthly_sales`. The scope
covers the existing PostgreSQL RAW tables, the four CLEAN views, the ANALYTICS
view, and the data tests executed by the full dbt build.

All database execution results below were supplied by the user from their
terminal. They were not executed or independently reproduced while preparing
this document. Model contracts and test definitions follow
[RS-031](RS-031.md); the supplied results record the database validation that
was pending in that document.

## Model dependencies and integration architecture

The transformation path starts from data already present in PostgreSQL:

```text
raw.orders      -> clean.orders      --+
                                      +-> analytics.monthly_sales
raw.order_items -> clean.order_items --+
raw.customers   -> clean.customers
raw.products    -> clean.products
```

All five models are materialized as views. The CLEAN models read their
corresponding RAW tables directly. `monthly_sales` uses only `ref('orders')`
and `ref('order_items')`; `customers` and `products` are included in the full
build but are not model ancestors of `monthly_sales`. Data tests can reference
multiple models without adding model dependencies to this aggregation.

The ANALYTICS contract selects delivered orders with non-NULL purchase
timestamps, assigns sales by purchase month, and joins their items by
`order_id`. A generated calendar includes every month between the first and
last eligible purchases. Orders without items still count as orders. The
schema configuration places the output at `analytics.monthly_sales`, as
described in RS-031.

## Commands executed and their purpose

The user reported these dbt commands in the project context:

```bash
dbt ls --select +monthly_sales --resource-type model --output name
dbt build
```

- `dbt ls` selects `monthly_sales` and its model ancestors. The supplied output
  was `monthly_sales`, `order_items`, and `orders`, confirming the model graph.
- `dbt build` builds the full project and executes its data tests, covering all
  five models rather than only the selected aggregation path.

After the build, the user queried `analytics.monthly_sales` to obtain the
calendar coverage, revenue, order count, item count, and months without
eligible sales. The exact SQL was not supplied. The following read-only query
expresses those checks for reference; it is not an execution transcript and
was not run while preparing this document:

```sql
SELECT
    COUNT(*) AS calendar_months,
    SUM(product_revenue) AS product_revenue,
    SUM(total_orders) AS delivered_orders,
    SUM(total_items) AS order_items,
    COUNT(*) FILTER (WHERE total_orders = 0) AS months_without_eligible_sales
FROM analytics.monthly_sales;
```

## Verified test results

The user-supplied `dbt build` result was successful:

| Measure | Reported result |

| Data tests | 61 |
| PASS | 66 |
| WARN | 0 |
| ERROR | 0 |
| SKIP | 0 |
| Duration | 8.52 seconds |

The 66 passing results comprise five view models and 61 data tests; they do
not represent 66 data tests. No model or test was skipped.

The existing `monthly_sales` suite contains five generic tests and seven
singular tests. These cover the unique, non-NULL month key; non-NULL revenue,
orders, and items; calendar completeness; global and per-month reconciliation;
zero-month behavior; average order value; column types; and delivered orders
without usable purchase dates. The remaining tests cover the CLEAN contracts.
The supplied full-build summary reports all 61 data tests passing.

## Business KPI reconciliation

The post-build query returned these values:

| KPI | Verified value | Business interpretation |
| --- | ---: | --- |
| Calendar months | 24 | Continuous monthly calendar between the first and last eligible purchases. |
| Product revenue | BRL 13,221,498.11 | Sum of eligible item prices, excluding freight. |
| Delivered orders | 96,478 | Distinct delivered orders with a usable purchase timestamp. |
| Order items | 110,197 | Matching item rows belonging to eligible orders. |
| Months without eligible sales | 1 | Calendar month with zero eligible orders. |

`assert_monthly_sales_totals` compares the summed ANALYTICS metrics with
independent CLEAN aggregates. It counts orders directly from `orders`, then
sums prices and counts item rows using `EXISTS` against eligible orders. This
avoids inflating the order count through the one-to-many item relationship.
`assert_monthly_sales_monthly_reconciliation` also compares each month, so
matching global totals cannot conceal sales assigned to the wrong month.
Their passing results support reconciliation of the reported KPIs to CLEAN.

The calendar and zero-month tests support retaining the one month without
eligible sales. Such a month has zero revenue, orders, and items, with NULL
`average_order_value`. A month with eligible orders but no contributing item
prices is not classified as a month without eligible sales.

Revenue uses PostgreSQL NUMERIC arithmetic without explicit model rounding;
the amount above is the supplied result expressed in BRL. Monthly average
order value is `product_revenue / NULLIF(total_orders, 0)`. No separate numeric
average-order-value result was supplied. The reported dataset totals are
observations for this run, not fixed assertions added to the model tests.

## Limitations

- CSV ingestion was not tested end-to-end in this verification. The dbt build
  starts from existing RAW tables; it does not establish that CSV loading,
  replacement, or rollback works against the database.
- Power BI was not tested end-to-end. Connection, refresh, semantic-model
  calculations, filters, and report visuals remain outside the verified scope.
- The results describe the dataset and environment used in the user's terminal
  run. As views, the models reflect their underlying data when queried; these
  figures are not a stored snapshot or a guarantee for later data changes.
