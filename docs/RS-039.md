# RS-039: Implement Customer Satisfaction Analytics

RS-039 implements RF-005: analyze order review scores, positive satisfaction,
and review coverage. It adds a record-preserving CLEAN reviews view and an
ANALYTICS view with one row per delivered order. Orders without valid reviews
remain visible and are not classified as negative feedback.

## Objective and scope

Complete customer satisfaction analysis for RetailSphere MVP v1.0 using the
existing PostgreSQL, dbt, and Power BI architecture. Business rules are
implementation assumptions made under the owner's authorization and remain
subject to manual Code Review.

Repository and database inspection confirmed that `raw.order_reviews` exists
with seven TEXT columns, but no CLEAN reviews model or dbt source declaration
existed. Only the necessary RAW reviews declaration was added. Existing CLEAN
and ANALYTICS model SQL, RAW records, ingestion, Docker configuration, macros,
and project configuration were preserved. No packages were installed. The
original implementation and read-only SQL validation did not execute dbt
commands, Git commands, or database-writing SQL. The owner subsequently
completed manual dbt validation, as recorded below.

```text

raw.orders                   -> clean.orders        --+-> analytics.customer_satisfaction
```

| ANALYTICS model | [`models/analytics/customer_satisfaction.sql`](../dbt/retailsphere/models/analytics/customer_satisfaction.sql) |

The CLEAN model uses `source('raw', 'order_reviews')` and the existing

review order IDs against `ref('orders')`. Both models inherit view
materialization. Existing schema configuration resolves CLEAN to `clean`
through the profile and ANALYTICS to literal `analytics` through the macro.

## Business rules and analytical grain

### Eligibility and interpretation

- Eligible orders have `order_status = 'delivered'`, with no timestamp or
  item/payment requirement. This aligns completed-order analysis with the
  other MVP models and RS-038. Reviews for other statuses remain in CLEAN but
  do not contribute to these KPIs.
- A valid review score is an integer from 1 through 5. Larger scores indicate
  a more positive review. This is an order review scale, not an NPS survey.
- A reviewed order has at least one valid linked score. A positive order has
  selected score 4 or 5; scores 1-3 are not positive. Score 3 is not silently
  removed from the denominator.
- The positive satisfaction denominator is reviewed eligible orders. Review
  coverage uses all eligible orders. Neither rate counts review records or
  unique customers.
- Reviews join to orders on original `order_id`. Unmatched reviews remain in
  CLEAN, fail its relationship test, and cannot contribute to an eligible
  order. No synthetic order or buyer is created.
- Orders do not require a customer join. A delivered order with a missing
  buyer identity still belongs in the order-satisfaction population; RS-038
  reports that identity problem separately.

### Multiple, duplicate, missing, and invalid reviews

CLEAN preserves every source record, including exact duplicates, repeated
review IDs, conflicting scores, original text, and absent values. Neither
`review_id` nor `order_id` has a CLEAN uniqueness test.

ANALYTICS selects one valid review per order using this explicit total order:

1. Latest typed `review_answer_timestamp`, NULL last.
2. Latest typed `review_creation_date`, NULL last.
3. Lexicographically smallest `review_id` under PostgreSQL `C` collation,
   NULL last, to make ordering independent of the database's default collation.
4. Lowest valid `review_score` when ID and both timestamps are identical.
   This conservative final fallback avoids optimistic selection when equally
   identified records conflict and no source version sequence is available.

Answer timestamp is the recency proxy for answered feedback; creation time
is secondary. Lexical IDs have no chronological meaning. Missing timestamps
do not invalidate a score; dated records sort first, with remaining ties
resolved by ID and score. If every ordering field is identical, all projected
review fields are identical, so exact duplicates cannot change the result.
Comments are not projected into ANALYTICS; they remain available in CLEAN.

Only valid scores participate in selection. A newer invalid review does not
replace an older valid score. Invalid and missing scores still contribute to
`review_record_count`, and valid duplicates still contribute to
`valid_review_count`. These counts expose source multiplicity without
weighting order KPIs by the number of reviews.

A NULL review ID does not invalidate a linked valid score. CLEAN's identifier
test reports the defect, while ANALYTICS uses score presence for coverage.
Never use `COUNT(selected_review_id)` as the reviewed-order KPI.

The grain is exactly one row per delivered `order_id`, relying on the existing
CLEAN order key contract. Orders without any valid score have NULL selected
review fields, `has_valid_review = FALSE`, and `is_positive_review = NULL`.
An order with valid score 1-3 has `is_positive_review = FALSE`. Empty eligible
input produces zero rows, zero aggregate counts, and undefined rates/average.

## CLEAN SQL implementation and columns

The `converted` CTE reads the declared source, preserves original text, and
guards casts with `pg_input_is_valid`. Malformed, missing, or overflowing
scores become NULL INTEGERs. Out-of-range integers remain typed and visible;
they fail `accepted_values` and are excluded from satisfaction selection.
The final projection adds the score-quality flag. No rows are filtered.

| Column | PostgreSQL type | Definition |
| --- | --- | --- |
| `review_id` | TEXT | Original source identifier; may repeat. |
| `order_id` | TEXT | Original order key; may repeat. |
| `review_score_raw` | TEXT | Original score text. |
| `review_score` | INTEGER | Safely converted score; NULL if absent or not representable as INTEGER. |
| `review_comment_title` | TEXT | Original optional title. |
| `review_comment_message` | TEXT | Original optional message. |
| `review_creation_date_raw` | TEXT | Original creation date/time. |
| `review_answer_timestamp_raw` | TEXT | Original answer timestamp. |
| `review_creation_date` | TIMESTAMP without time zone | Safely converted creation value; NULL if missing/invalid. |
| `review_answer_timestamp` | TIMESTAMP without time zone | Safely converted answer value; NULL if missing/invalid. |
| `is_review_creation_date_invalid` | BOOLEAN | Non-NULL source creation input rejected by the existing timestamp macro. |
| `is_review_answer_timestamp_invalid` | BOOLEAN | Non-NULL source answer input rejected by the existing timestamp macro. |
| `is_review_score_invalid` | BOOLEAN | Non-NULL source score that cannot be typed or is outside 1-5. |

Source NULLs produce FALSE quality flags. Empty strings are non-NULL inputs
and are invalid when conversion rejects them. Retaining original text makes
missing, malformed, and out-of-range inputs auditable without changing RAW.

## ANALYTICS SQL implementation and columns

`review_counts` groups all CLEAN records by order and counts valid scores.
`ranked_valid_reviews` uses `ROW_NUMBER()` over valid scores with the selection
policy above. The final query left joins the per-order counts and the single
winning row to delivered orders. Both joins have at most one row per order,
so repeated reviews cannot multiply the eligible population.

| Column | PostgreSQL type | Definition |
| --- | --- | --- |
| `order_id` | TEXT | Unique delivered-order key. |
| `order_purchase_timestamp` | TIMESTAMP without time zone | CLEAN purchase timestamp, including NULL; supports order-cohort filtering. |
| `review_record_count` | BIGINT | All linked source review records, including duplicates and invalid scores; zero without records. |
| `valid_review_count` | BIGINT | Linked records with score 1-5, including duplicates; zero without valid scores. |
| `selected_review_id` | TEXT | Winning review ID; nullable and not unique across orders. |
| `review_score` | INTEGER | Winning score 1-5; NULL without a valid review. |
| `review_creation_date` | TIMESTAMP without time zone | Winning review's typed creation value. |
| `review_answer_timestamp` | TIMESTAMP without time zone | Winning review's typed answer value. |
| `has_valid_review` | BOOLEAN | TRUE when a winning valid score exists; never NULL. |
| `is_positive_review` | BOOLEAN, nullable | TRUE for 4-5, FALSE for 1-3, NULL without a valid score. |

## KPI formulas and Power BI usage

Define measures over the order-grain view. Percentages and averages are
calculated after filters; they are not repeated as order columns.

| KPI | SQL formula over `analytics.customer_satisfaction` |
| --- | --- |
| Eligible orders | `COUNT(*)` |
| Reviewed orders | `COUNT(*) FILTER (WHERE has_valid_review)` |
| Orders without valid reviews | `COUNT(*) FILTER (WHERE NOT has_valid_review)` |
| Review coverage (%) | `100::NUMERIC * COUNT(*) FILTER (WHERE has_valid_review) / NULLIF(COUNT(*), 0)` |
| Average review score | `AVG(review_score)`; valid selected scores only |
| Score distribution, each `n` from 1 to 5 | `COUNT(*) FILTER (WHERE review_score = n)` |
| Positive reviewed orders | `COUNT(*) FILTER (WHERE is_positive_review)` |
| Positive satisfaction (%) | `100::NUMERIC * COUNT(*) FILTER (WHERE is_positive_review) / NULLIF(COUNT(*) FILTER (WHERE has_valid_review), 0)` |

Recommended DAX, using table name `customer_satisfaction`:

```dax
Eligible Orders =
    COALESCE(COUNTROWS('customer_satisfaction'), 0)

Reviewed Orders =
    CALCULATE(
        [Eligible Orders],
        KEEPFILTERS('customer_satisfaction'[has_valid_review] = TRUE())
    )

Orders Without Valid Reviews =
    [Eligible Orders] - [Reviewed Orders]

Review Coverage =
    DIVIDE([Reviewed Orders], [Eligible Orders])

Average Review Score =
    AVERAGE('customer_satisfaction'[review_score])

Positive Reviewed Orders =
    CALCULATE(
        [Eligible Orders],
        KEEPFILTERS('customer_satisfaction'[is_positive_review] = TRUE())
    )

Positive Satisfaction Rate =
    DIVIDE([Positive Reviewed Orders], [Reviewed Orders])
```

Format the two rate measures as Percentage without multiplying by 100.
`DIVIDE` returns BLANK for zero denominators; empty populations have zero
count measures and BLANK rates/average. Keep full precision until display.

Use `review_score` as a categorical axis with summarization disabled and
`[Reviewed Orders]` as the value to show scores 1-5. Display unreviewed orders
separately. For zero-count score categories, use a 1-5 score dimension in a
future semantic model if needed. A score-percentage distribution should use
all reviewed orders in the same order cohort as its denominator; remove only
the score-axis filter when defining that denominator.

Use headline coverage cards without score/positive-only filters; such filters
remove unreviewed orders and change the population. `KEEPFILTERS` otherwise
preserves the current visual context. The order count measure is additive
over disjoint order cohorts. Averages and percentages must be recomputed from
underlying scores/counts rather than averaged across groups.

The view can relate to the existing order model on unique `order_id` without
joining raw reviews into it. Avoid fact-to-fact joins through order items that
multiply order rows. An optional date dimension should filter by purchase
date for order-cohort analysis; review answer date answers a different time
question. NULL purchase timestamps remain eligible and need an explicit
unknown-date treatment if a date slicer is introduced. Do not infer the number
of satisfied unique buyers from positive order counts. Power BI implementation
and relationship validation remain outside these tickets.

## Data quality tests

The relevant YAML additions use existing `data_tests` syntax and dbt's
`arguments` structure. There are no new packages or custom test macros.

Seven generic CLEAN tests require review/order IDs and the three quality
flags to be non-NULL, validate the order relationship, and accept only integer
scores 1-5 when non-NULL. Missing scores are deliberately permitted. Malformed
inputs converted to NULL remain exposed by flags; conversion tests verify
their treatment rather than requiring all flags to be FALSE. Invalid typed
scores fail the accepted-values test. Quality flags should be monitored during
manual review even when conversion is working correctly.

Seven generic ANALYTICS tests cover order uniqueness, non-NULL order IDs,
order referential integrity, non-NULL record/valid counts, selected scores
1-5 when present, and non-NULL `has_valid_review`. Selected review IDs,
timestamps, scores, and positive flags deliberately allow NULL.

Seven singular tests implement source preservation and satisfaction checks:

| Test | Assertion |
| --- | --- |
| [`assert_order_reviews_preserve_source_records.sql`](../dbt/retailsphere/tests/assert_order_reviews_preserve_source_records.sql) | Bidirectional `EXCEPT ALL` compares all original source fields, including duplicates, NULLs and comments, against CLEAN's preserved text. This also reconciles record counts without a unique-key assumption. |
| [`assert_order_reviews_conversion.sql`](../dbt/retailsphere/tests/assert_order_reviews_conversion.sql) | Independently spell out guarded source casts and flags, then compare typed multisets in both directions; does not reuse the CLEAN timestamp macros. |
| [`assert_order_reviews_nonblank_identifiers.sql`](../dbt/retailsphere/tests/assert_order_reviews_nonblank_identifiers.sql) | Reject NULL, empty, and whitespace-only review/order IDs while preserving source rows. |
| [`assert_customer_satisfaction_population.sql`](../dbt/retailsphere/tests/assert_customer_satisfaction_population.sql) | Independently aggregate RAW review counts and valid-score counts, then FULL OUTER JOIN delivered CLEAN orders to ANALYTICS to detect missing/extra orders, wrong counts, and changed purchase timestamps. |
| [`assert_customer_satisfaction_selection.sql`](../dbt/retailsphere/tests/assert_customer_satisfaction_selection.sql) | Recompute winners using PostgreSQL `DISTINCT ON` instead of `ROW_NUMBER`; NULL-safe comparison verifies all selected review fields and missing-review behavior. |
| [`assert_customer_satisfaction_classification.sql`](../dbt/retailsphere/tests/assert_customer_satisfaction_classification.sql) | Reject negative/missing counts, valid counts exceeding records, invalid scores, inconsistent coverage flags, and positive flags that fail the nullable 4-5 rule. |
| [`assert_customer_satisfaction_metrics.sql`](../dbt/retailsphere/tests/assert_customer_satisfaction_metrics.sql) | Independently type and select RAW reviews, join RAW delivered orders, and reconcile eligible/reviewed/positive counts, exact average, the five-bin distribution, coverage, and positive-rate formulas. |

### Reproduce source profiling

These read-only queries reproduce key diagnostics. Equivalent SELECT queries
were used for the observed profiling above; no database mutations are needed.

```sql
SELECT
    COUNT(*) AS review_records,
    COUNT(DISTINCT review_id) AS distinct_review_ids,
    COUNT(DISTINCT order_id) AS distinct_reviewed_orders,
    COUNT(*) FILTER (WHERE review_score IS NULL) AS null_scores,
    COUNT(*) FILTER (
        WHERE review_score IS NOT NULL
          AND NOT pg_input_is_valid(review_score, 'integer')
    ) AS malformed_scores,
    COUNT(*) FILTER (
        WHERE CASE WHEN pg_input_is_valid(review_score, 'integer')
            THEN review_score::INTEGER NOT BETWEEN 1 AND 5 ELSE FALSE END
    ) AS out_of_range_scores
FROM raw.order_reviews;

SELECT review_score, COUNT(*) AS review_records
FROM raw.order_reviews
GROUP BY review_score
ORDER BY review_score;

SELECT review_id, COUNT(*) AS review_records,
    COUNT(DISTINCT order_id) AS distinct_orders
FROM raw.order_reviews
GROUP BY review_id
HAVING COUNT(*) > 1;

SELECT order_id, COUNT(*) AS review_records,
    COUNT(DISTINCT review_score) AS distinct_scores
FROM raw.order_reviews
GROUP BY order_id
HAVING COUNT(*) > 1;

SELECT COUNT(*) AS unmatched_review_records
FROM raw.order_reviews AS r
LEFT JOIN clean.orders AS o ON r.order_id = o.order_id
WHERE o.order_id IS NULL;

SELECT COUNT(*) AS delivered_orders_without_reviews
FROM clean.orders AS o
WHERE o.order_status = 'delivered'
  AND NOT EXISTS (
      SELECT 1 FROM raw.order_reviews AS r WHERE r.order_id = o.order_id
  );
```

### Reproduce independent order-level benchmarks

This RAW-based SELECT implements guarded conversions and `DISTINCT ON`
selection independently of the analytics model's window function. The policy
matches the final implementation, including the lower-score last tie-breaker.

```sql
WITH typed_reviews AS (
    SELECT
        order_id,
        review_id,
        CASE WHEN pg_input_is_valid(review_score, 'integer')
            THEN review_score::INTEGER END AS review_score,
        CASE WHEN pg_input_is_valid(review_creation_date, 'timestamp without time zone')
            THEN review_creation_date::TIMESTAMP END AS review_creation_date,
        CASE WHEN pg_input_is_valid(review_answer_timestamp, 'timestamp without time zone')
            THEN review_answer_timestamp::TIMESTAMP END AS review_answer_timestamp
    FROM raw.order_reviews
),
winners AS (
    SELECT DISTINCT ON (order_id) order_id, review_score
    FROM typed_reviews
    WHERE review_score BETWEEN 1 AND 5
    ORDER BY order_id,
        review_answer_timestamp DESC NULLS LAST,
        review_creation_date DESC NULLS LAST,
        review_id COLLATE "C" ASC NULLS LAST,
        review_score ASC
)
SELECT
    COUNT(*) AS eligible_orders,
    COUNT(w.review_score) AS reviewed_orders,
    COUNT(*) FILTER (WHERE w.review_score IS NULL) AS orders_without_valid_reviews,
    AVG(w.review_score) AS average_review_score,
    COUNT(*) FILTER (WHERE w.review_score = 1) AS score_1_orders,
    COUNT(*) FILTER (WHERE w.review_score = 2) AS score_2_orders,
    COUNT(*) FILTER (WHERE w.review_score = 3) AS score_3_orders,
    COUNT(*) FILTER (WHERE w.review_score = 4) AS score_4_orders,
    COUNT(*) FILTER (WHERE w.review_score = 5) AS score_5_orders,
    COUNT(*) FILTER (WHERE w.review_score >= 4) AS positive_reviewed_orders,
    100::NUMERIC * COUNT(w.review_score) / NULLIF(COUNT(*), 0) AS coverage_pct,
    100::NUMERIC * COUNT(*) FILTER (WHERE w.review_score >= 4)
        / NULLIF(COUNT(w.review_score), 0) AS positive_satisfaction_pct
FROM raw.orders AS o
LEFT JOIN winners AS w USING (order_id)
WHERE o.order_status = 'delivered';
```

The following read-only query checks output KPIs directly. The original
validation executed equivalent SQL against the rendered CTE only. The owner
subsequently built and queried `analytics.customer_satisfaction`, confirming
the view results above; the positive satisfaction percentage was calculated
from the confirmed counts because its preview column was truncated.

```sql
SELECT
    COUNT(*) AS eligible_orders,
    COUNT(*) FILTER (WHERE has_valid_review) AS reviewed_orders,
    COUNT(*) FILTER (WHERE NOT has_valid_review) AS orders_without_valid_reviews,
    AVG(review_score) AS average_review_score,
    COUNT(*) FILTER (WHERE is_positive_review) AS positive_reviewed_orders,
    100::NUMERIC * COUNT(*) FILTER (WHERE has_valid_review)
        / NULLIF(COUNT(*), 0) AS coverage_pct,
    100::NUMERIC * COUNT(*) FILTER (WHERE is_positive_review)
        / NULLIF(COUNT(*) FILTER (WHERE has_valid_review), 0) AS positive_satisfaction_pct
FROM analytics.customer_satisfaction;
```

## Limitations and remaining risks

- Delivered-only eligibility intentionally excludes feedback about canceled,
  unavailable, or still-in-progress orders. These reviews remain in CLEAN;
  overall marketplace experience could require a separate population later.
- Positive satisfaction is the share of reviewed orders scoring 4-5. It is
  not NPS, a unique-customer satisfaction rate, or a measure of all customers'
  opinions. Non-response bias can remain despite high review coverage.
- The latest-valid-review policy is an explicit assumption, not an inferred
  review-version contract. Source IDs are not version numbers. The final
  lower-score tie-breaker is conservative and should be revisited if reliable
  source sequencing becomes available. No timestamp tie groups were observed
  in current profiling, but future inputs can contain them.
- Invalid/missing timestamps lose recency information; invalid and missing
  scores reduce review coverage. Original values and flags are retained for
  diagnosis. Malformed values can be safely represented without making the
  dataset defect-free.
- `review_record_count` and `valid_review_count` include duplicate records by
  design. Their sums are review-record metrics, never reviewed-order counts.
- Upstream order uniqueness is a prerequisite. These models do not repair
  conflicting keys, identity mappings, ingestion defects, or RAW data.
- Timestamps retain the existing timestamp-without-time-zone semantics; no
  timezone conversion or date repair was introduced.
- The owner completed dbt parse, full build, all 108 data tests, and direct
  ANALYTICS view checks. Power BI implementation and refresh validation remain
  pending; the completed checks do not establish Power BI behavior or
  performance at larger scale.
- The business assumptions, selected-review policy, and final Power BI filter
  behavior require human review. There is no unresolved implementation blocker.
