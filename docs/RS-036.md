# RS-036: Implement Category Sales Analytics Model

Sprint 07 adds `analytics.category_sales`, a view for analyzing product revenue,
distinct delivered orders, and sold items by product category. It supports
category performance comparisons while retaining sales whose product category
is missing.

## Objective and scope

The model aggregates data already available in PostgreSQL through the
RAW -> CLEAN -> ANALYTICS architecture. This document describes the existing
implementation and its tests; it does not change transformation logic.

The SQL models, YAML test definitions, singular tests, schema macro, saved dbt
artifacts, and execution log were inspected before documenting the results.
The metrics below are supplied story results also present in the saved log.
The integration result is supported by `target/run_results.json` and the log.
No database commands were executed while preparing this document.

## Architecture and dependencies

```text
raw.orders      -> clean.orders      --+
raw.order_items -> clean.order_items --+-> analytics.category_sales
raw.products    -> clean.products    --+
```

The implementation is
[`category_sales.sql`](../dbt/retailsphere/models/analytics/category_sales.sql).
Its three dependencies are resolved through dbt `ref()`:

| dbt reference | Relation | Contribution |
| --- | --- | --- |
| `ref('orders')` | `clean.orders` | Order identifier and delivered status. |
| `ref('order_items')` | `clean.order_items` | Order/product identifiers, item identifiers, and typed item prices. |
| `ref('products')` | `clean.products` | Product identifier and original category name, including NULL. |

CLEAN models read the corresponding RAW tables. The category model joins
products to items on `product_id`, then items to orders on `order_id`, using
inner joins. It reads CLEAN exclusively through `ref()` rather than hardcoded
relation names. These references establish the model dependencies and allow
dbt to resolve relations and build them in dependency order.

The analytics folder configuration materializes the model as a view. The
existing `generate_schema_name` macro places it in the literal `analytics`
schema; the saved manifest resolves it to
`"retailsphere"."analytics"."category_sales"`. The full project also contains
`clean.customers` and `analytics.monthly_sales`, which are not ancestors of
`category_sales`.

## Business rules and aggregation grain

- Include only orders where `order_status = 'delivered'`. Eligibility does not
  depend on purchase or delivery timestamps, and there is no date filter.
- Calculate product revenue as `SUM(oi.price)`, excluding `freight_value`.
  CLEAN provides NUMERIC prices; the model applies no explicit rounding.
- Produce one row per category represented by eligible joined items. Categories
  without delivered sales do not receive a zero-filled row.
- Apply `COALESCE(p.product_category_name, 'unknown')` in both the SELECT and
  GROUP BY. Missing category names are represented as lowercase `unknown`
  only in ANALYTICS; RAW and CLEAN retain their original values.
- Count distinct order IDs within each category. An order containing products
  from several categories contributes once to each relevant category. Summing
  category order counts therefore does not produce a global distinct-order
  count.
- Count sold items with `COUNT(oi.order_item_id)`. Item IDs are unique within an
  order, not across all orders, so `COUNT(DISTINCT order_item_id)` would be
  incorrect. The existing CLEAN contract requires non-NULL item IDs and unique
  `(order_id, order_item_id)` pairs.

The model depends on unique, non-NULL CLEAN order and product IDs to avoid
join multiplication. Orders without matching items cannot contribute to a
category, and items without a matching product are excluded by the inner join.
An existing product with a NULL category is retained under `unknown`.

## Output columns

| Column | PostgreSQL type | Definition |
| --- | --- | --- |
| `product_category_name` | TEXT | Category grouping key: `COALESCE(p.product_category_name, 'unknown')`. Unique and non-NULL. |
| `total_orders` | BIGINT | `COUNT(DISTINCT o.order_id)` for delivered orders with items in this category. |
| `total_items` | BIGINT | `COUNT(oi.order_item_id)` across eligible joined item rows in this category. |
| `product_revenue` | NUMERIC | `SUM(oi.price)` for the category, expressed in BRL and excluding freight; no fixed precision, scale, or explicit rounding. |

Counts and sums describe the current underlying data because the output is a
view, rather than a stored snapshot. Revenue relies on the existing CLEAN
checks for valid, non-NULL prices; SQL `SUM` ignores NULL prices.

## Data quality tests

The project uses generic `data_tests` in
[`models/analytics/schema.yml`](../dbt/retailsphere/models/analytics/schema.yml)
and singular `assert_*.sql` queries that return only violations.

The category model has five generic tests:

| Test | Column | Purpose |
| --- | --- | --- |
| `unique` | `product_category_name` | Enforce one row per category. |
| `not_null` | `product_category_name` | Require a category key, including the `unknown` fallback. |
| `not_null` | `total_orders` | Require an order count. |
| `not_null` | `total_items` | Require an item count. |
| `not_null` | `product_revenue` | Require a revenue value. |

Two singular tests reconcile global totals against independent CLEAN
aggregates:

- [`assert_category_sales_items.sql`](../dbt/retailsphere/tests/assert_category_sales_items.sql)
  compares `SUM(category_sales.total_items)` with `COUNT(*)` from CLEAN items
  joined to delivered CLEAN orders.
- [`assert_category_sales_revenue.sql`](../dbt/retailsphere/tests/assert_category_sales_revenue.sql)
  compares `SUM(category_sales.product_revenue)` with `SUM(oi.price)` from the
  same delivered CLEAN order/item population, excluding freight.

Each test builds one CLEAN aggregate row and one ANALYTICS aggregate row,
combines them with `CROSS JOIN`, and uses `IS DISTINCT FROM` to return a row
only when the totals differ. These are exact comparisons with no tolerance or
rounding. Unlike ordinary inequality, `IS DISTINCT FROM` also detects a
NULL/non-NULL mismatch. The CLEAN baselines do not join products, so they can
expose item or revenue loss caused by the additional product join.

All seven category tests passed in the recorded integration build. These tests
reconcile global items and revenue; they do not independently reconcile every
category or assert the reported `unknown` metrics as fixed constants.

## Key technical learnings

- **Aggregation grain:** Define the output grain before choosing aggregates.
  Category order counts require distinct order IDs, while sold items count
  item rows. Orders can span categories, so order counts are not additive
  across categories even though item counts and revenue are.
- **`COALESCE`:** Apply the category fallback consistently in projection and
  grouping. Handling NULL at the reporting layer preserves source values and
  CLEAN lineage.
- **`ref()`:** Reference dbt model names to declare dependencies and resolve
  their configured relations, supporting correct build order and lineage.
- **`CROSS JOIN`:** Combine two single-row aggregate results for reconciliation
  without needing a join key. This is safe here because both CTEs aggregate
  the entire population without GROUP BY.
- **`IS DISTINCT FROM`:** Compare aggregate results with NULL-aware semantics.
  A mismatch involving NULL must produce a failing row rather than disappear
  because a normal comparison evaluates to unknown.

## Remaining limitations

- Validation starts from existing PostgreSQL RAW tables. End-to-end CSV
  ingestion, replacement, and rollback were not tested by this story's build.
- Power BI connections, refreshes, semantic models, and report visuals were
  not tested end-to-end.
- Global reconciliation cannot detect category misassignments that preserve
  total items and revenue. There is no dedicated per-category reconciliation
  or distinct-order reconciliation test in the category suite.
- `COALESCE` replaces NULL only; it does not normalize empty strings,
  whitespace, spelling, or translate category names. A literal source category
  named `unknown` would share the fallback group.
- The model does not deduplicate or repair invalid upstream records. CLEAN
  key, relationship, item, and price checks remain prerequisites for reliable
  results. Generic non-NULL tests alone do not establish numeric ranges.
- Empty-input behavior has not been demonstrated with synthetic data. With no
  eligible items, the view returns no rows; the item reconciliation compares
  CLEAN `COUNT(*) = 0` with ANALYTICS `SUM(total_items) = NULL` and fails. The
  revenue reconciliation compares two NULL sums and would pass.
- Views recalculate against their underlying data. Recorded metrics may change,
  performance at larger volumes is unverified, and the literal `analytics`
  schema requires separate databases to isolate targets sharing a schema name.
