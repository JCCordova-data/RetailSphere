# RS-037: Implement Delivery Performance Analytics

RS-037 adds `analytics.delivery_performance`, a view that supports RF-004:
identify late deliveries. It summarizes delivered orders, calendar-date
punctuality, missing delivery dates, the late delivery percentage, and the
average calendar days late.

## Objective and scope

Implement the approved delivery performance contract using the existing
RAW -> CLEAN -> ANALYTICS architecture. Business analysis and source profiling
were supplied with the ticket. The benchmark values below are observations
for the current dataset, not constants in the model or tests.

This change adds one analytics model, extends the existing analytics YAML,
and adds four singular tests. It does not alter RAW, CLEAN, existing analytics
models, dependencies, or project configuration.

## Architecture and dependencies

```text
raw.orders -> clean.orders -> analytics.delivery_performance
```

The implementation is
[`delivery_performance.sql`](../dbt/retailsphere/models/analytics/delivery_performance.sql).
It reads CLEAN exclusively through `ref('orders')`, which declares the dbt
dependency and resolves the configured relation. No item or product joins are
needed, so one-to-many relationships cannot multiply the delivered population.

The existing analytics folder configuration materializes the model as a view.
The existing `generate_schema_name` macro resolves its schema to `analytics`;
the parsed manifest resolves the relation to
`"retailsphere"."analytics"."delivery_performance"`.

## Business rules and aggregation grain

- Include only orders where `order_status = 'delivered'`, without a date window.
- Cast `order_delivered_customer_date` and `order_estimated_delivery_date` to
  `DATE` before comparing them or calculating calendar-day differences.
- An actual date before the estimate is `early`; equal dates are `on_time`;
  an actual date after the estimate is `late`. Different times on the same
  calendar day remain on time.
- A delivered order missing either date is not evaluable. Retain it in
  `total_delivered_orders` and count it once in `missing_delivery_dates`,
  including when both dates are NULL. It contributes to no delivery class.
- Use evaluable delivered orders as the late-rate denominator. Multiply by
  numeric 100 to produce a percentage, use `NULLIF` to prevent division by
  zero, and round to two decimal places.
- Average calendar-day differences only for late orders, rounded to two decimal
  places. `AVG` over no late orders returns NULL; this remains NULL rather than
  becoming zero.

The grain is exactly one global summary row. The aggregate has no `GROUP BY`,
so it also returns one row when no delivered orders exist. All six counts are
then zero, while the percentage and average are NULL. If evaluable orders exist
but none are late, the percentage is `0.00` and the average remains NULL.

## Output columns

| Column | PostgreSQL type | Definition |
| --- | --- | --- |
| `total_delivered_orders` | BIGINT | Count of all delivered CLEAN order rows. |
| `evaluable_delivered_orders` | BIGINT | Count of delivered rows with both dates present. |
| `missing_delivery_dates` | BIGINT | Count of delivered rows with either or both dates missing; counts orders, not individual missing fields. |
| `early_deliveries` | BIGINT | Count with actual DATE before estimated DATE. |
| `on_time_deliveries` | BIGINT | Count with actual DATE equal to estimated DATE. |
| `late_deliveries` | BIGINT | Count with actual DATE after estimated DATE. |
| `late_delivery_rate_pct` | NUMERIC | `ROUND(100::NUMERIC * late_deliveries / NULLIF(evaluable_delivered_orders, 0), 2)`; 0-100 when defined, NULL with no evaluable orders. |
| `avg_late_days` | NUMERIC | `ROUND(AVG(actual_delivery_date - estimated_delivery_date) FILTER (WHERE delivery_class = 'late'), 2)`; NULL with no late orders. |

Both numeric metrics use a consistent two-decimal rounding policy without a
fixed NUMERIC precision cap. PostgreSQL DATE subtraction returns an integer
number of calendar days; its average is NUMERIC, preserving fractional means.
Counts rely on the existing CLEAN unique, non-NULL `order_id` contract. The
model counts source rows without deduplication or repair.

## Data quality tests

The project uses generic `data_tests` in
[`models/analytics/schema.yml`](../dbt/retailsphere/models/analytics/schema.yml)
and singular `assert_*.sql` queries that return only violations.

Six generic `not_null` tests require all count columns to be populated. The
percentage and average deliberately permit NULL because those values are
undefined for the populations described above. They have no `not_null` test.

Four singular tests use `ref()` for model dependencies and return zero rows
when their assertions pass:

| Test | Purpose |
| --- | --- |
| [`assert_delivery_performance_population.sql`](../dbt/retailsphere/tests/assert_delivery_performance_population.sql) | Require exactly one summary row; independently aggregate delivered, evaluable, and missing-date CLEAN populations; check `total = evaluable + missing`. |
| [`assert_delivery_performance_classes.sql`](../dbt/retailsphere/tests/assert_delivery_performance_classes.sql) | Require `early + on_time + late = evaluable`. |
| [`assert_delivery_performance_late_count.sql`](../dbt/retailsphere/tests/assert_delivery_performance_late_count.sql) | Independently count delivered CLEAN orders with actual `::DATE` greater than estimated `::DATE`, then reconcile the late count. |
| [`assert_delivery_performance_metrics.sql`](../dbt/retailsphere/tests/assert_delivery_performance_metrics.sql) | Verify the rounded percentage and its NULL behavior, independently aggregate average late calendar days from CLEAN, and reject negative counts or percentages outside 0-100. |

The reconciliations use `IS DISTINCT FROM` so NULL/non-NULL mismatches produce
failures. The population test aggregates the view before comparison, allowing
it to detect zero or multiple summary rows. Tests derive expectations from
current data; none hardcode the supplied benchmark totals.

## Key technical learnings

- **Calendar-date semantics:** Cast before comparison and subtraction. A late
  timestamp on the estimated day is still on time, and a two-minute difference
  across midnight can represent one calendar day late.
- **Population accounting:** Preserve non-evaluable orders separately from
  class counts so missing dates do not silently improve the late percentage.
- **Numeric and NULL semantics:** Numeric multiplication avoids integer
  division; `NULLIF` protects an empty denominator. A NULL average communicates
  that no late-order population exists.
- **Independent reconciliation:** Derive expected populations and late orders
  directly from CLEAN without reusing the model's classification expression.

## Remaining limitations

- The view describes the full current delivered population without a time,
  geography, carrier, or product breakdown. It does not identify individual
  late order IDs in its output.
- Calendar days include weekends and holidays. This is not elapsed 24-hour
  duration, business-day lateness, or a timezone conversion.
- CLEAN timestamps have no timezone. The model uses their stored calendar
  dates and performs no additional timestamp normalization.
- Missing or invalid source timestamps converted to NULL by CLEAN are counted
  as non-evaluable. Analytics does not repair them or distinguish absent source
  values from conversion failures. A zero missing-estimate benchmark is not a
  permanent data quality assumption.
- Existing CLEAN key and conversion checks remain prerequisites. This model
  does not deduplicate orders or validate upstream ingestion. The full project,
  CSV ingestion, Power BI integration, and performance at larger volumes were
  not validated by the selected build.
- Class reconciliation checks their total; independent current-data aggregation
  verifies late orders specifically. There are no separate current-data early
  and on-time count reconciliations; calendar boundaries are covered by fixtures.
- Views recalculate against underlying data, so the observed benchmark metrics
  can change. Percentage and average values are rounded presentation metrics.
