# RS-021: ingesta RAW generalizada

## Arquitectura y contratos

`src/raw_datasets.py` declara nueve configuraciones inmutables: archivo fuente,
esquema/tabla destino, columnas ordenadas y filas esperadas. `src/ingest_raw.py`
implementa un único motor y el CLI; no hay scripts separados por dataset.
`src/ingest_orders.py` adapta la API y el comando de RS-020 al mismo motor.
`src/profile_csv.py` sigue siendo una herramienta independiente de exploración:
no se usa para cargar ni para deduplicar y no fue modificado.

| Dataset / tabla en `raw` | CSV | Filas de datos esperadas |
| --- | --- | ---: |
| customers | olist_customers_dataset.csv | 99441 |
| geolocation | olist_geolocation_dataset.csv | 1000163 |
| order_items | olist_order_items_dataset.csv | 112650 |
| order_payments | olist_order_payments_dataset.csv | 103886 |
| order_reviews | olist_order_reviews_dataset.csv | 99224 |
| orders | olist_orders_dataset.csv | 99441 |
| products | olist_products_dataset.csv | 32951 |
| sellers | olist_sellers_dataset.csv | 3095 |
| product_category_name_translation | product_category_name_translation.csv | 71 |

Cada ingesta valida el encabezado exacto y ordenado, el número de campos de cada
registro lógico y el conteo antes de obtener credenciales o conectarse. Los
registros con saltos de línea entre comillas cuentan como una fila. Los registros
vacíos, encabezados desordenados y CSV malformados se rechazan.

Después abre una conexión Psycopg 3 con `autocommit=False`, bloquea exclusivamente
la tabla, verifica nombres/orden/tipos TEXT, ejecuta `TRUNCATE` sin `CASCADE` y
transmite el CSV original en bloques de hasta 64 Ki caracteres mediante
`COPY ... FORMAT CSV, HEADER MATCH`. Verifica `count(*)` antes del commit. Una
excepción provoca rollback mediante el contexto de conexión y cierra la conexión.
No se ejecuta DDL desde Python.

No se recortan espacios, convierten números/fechas, corrigen nombres ni eliminan
duplicados. Se conservan ceros iniciales, Unicode y los nombres originales
`product_name_lenght` y `product_description_lenght`. Se acepta UTF-8 con BOM
inicial, que se elimina al decodificar, y se preservan los saltos de línea del
contenido. Se mantiene la semántica CSV de PostgreSQL de RS-020: un campo vacío
sin comillas representa NULL; `""` representa una cadena vacía; `NULL` es texto
literal. Todas las columnas destino son TEXT y admiten NULL.

## Uso del CLI

Desde la raíz del repositorio, con Python y las dependencias instaladas:

```bash
python -m src.ingest_raw --help
python -m src.ingest_raw customers --dry-run
python -m src.ingest_raw all --dry-run --source-dir /ruta/a/csvs
```

`--dry-run` solo lee/valida CSVs y muestra archivos, destinos y conteos; no consulta
credenciales, abre conexiones ni comprueba la estructura real de las tablas.
Sin `--dry-run` o `--replace`, el CLI termina antes de realizar trabajo. Ambos
modos son mutuamente excluyentes. Los nombres de dataset son los de la tabla
anterior; `all` los recorre en ese orden y se detiene ante el primer error.

Los siguientes comandos **reemplazan registros existentes** y se incluyen solo
para una futura ejecución autorizada durante el despliegue:

```bash
python -m src.ingest_raw customers --replace
python -m src.ingest_raw all --replace
```

El CLI muestra `raw.<tabla>` y el aviso `REPLACE (TRUNCATE + COPY)` antes de cargar.
Cada dataset usa una transacción independiente; `all` no es una transacción
global. Si falla el quinto dataset, los cuatro anteriores pueden haber quedado
confirmados. La salida informa cada commit y advierte sobre commits anteriores
al fallar. Una ejecución repetida reemplaza, no acumula filas.

`PGUSER`, `PGDATABASE` y `PGPASSWORD` deben estar en el entorno del proceso;
`PGHOST` y `PGPORT` tienen los valores predeterminados `127.0.0.1` y `5432`.
No se carga `.env` automáticamente ni se imprimen ajustes de conexión o errores
del driver, que podrían contener secretos o valores de entrada. El operador
debe verificar por separado el servidor y la base elegidos. No poner contraseñas
en comandos, archivos versionados, capturas ni logs.

## Compatibilidad RS-020

Se conservan `COLUMNS`, `CSV_PATH`, `EXPECTED_ROWS`, `connection_settings()`,
`validate_csv(file, expected_rows)`, la firma de `ingest_orders(...)` y el mensaje
de éxito original. Los argumentos de destino permiten seguir utilizando tablas
aisladas de prueba. Las ocho pruebas offline originales de ingesta pasan sin
modificaciones. El comando histórico `python src/ingest_orders.py` conserva su
comportamiento de reemplazo inmediato de `raw.orders`; para operaciones nuevas
se recomienda el CLI con `--replace` explícito. Los módulos también admiten
invocación directa como scripts y su importación no abre conexiones.

## Verificación offline e integración pendiente

Ejecutar únicamente los módulos offline mediante patrones exactos evita activar
accidentalmente pruebas de integración si existe una variable opt-in heredada:

```bash
python -m unittest discover -s tests -p test_ingest_orders.py -v
python -m unittest discover -s tests -p test_ingest_raw.py -v
python -m unittest discover -s tests -p test_profile_csv.py -v
python -m unittest discover -s tests -p test_explore_orders.py -v
```

Las pruebas RS-021 usan archivos temporales sintéticos y conexiones simuladas:
cubren los nueve contratos, concordancia estática del DDL, rechazo previo a la
conexión, metadatos inválidos antes de TRUNCATE, propagación de fallos de COPY y
conteo al contexto transaccional, preservación de contenido, repetición y CLI.
El resultado del conjunto offline es **37 pruebas aprobadas**, incluidas las
ocho originales de RS-020. Esto no prueba rollback real en PostgreSQL.

`tests/test_ingest_orders_integration.py` conserva la prueba RS-020 y añade otra
para los nueve contratos, repetición, valores y rollback después de un fallo de
COPY. **No se ejecutó**. Reutiliza el opt-in `RS020_RUN_INTEGRATION=1` y exige
todos los ajustes `RS020_TEST_PG{HOST,PORT,DATABASE,USER,PASSWORD}`, sin recurrir a
los `PG*` de la aplicación. Requiere PostgreSQL 18, una base dedicada terminada
en `_test`, un esquema `rs020_test` precreado y un usuario no superusuario con
USAGE/CREATE allí y sin privilegios sobre ninguna tabla RAW configurada.
Comprueba esas condiciones con una transacción de solo lectura antes de crear
tablas. Solo crea/trunca/elimina tablas de nombre único dentro de `rs020_test`,
sin eliminar esquemas ni usar CASCADE. No ejecuta la migración de producción.

4. Revisar y aplicar manualmente `sql/021_create_raw_tables.sql` al destino
   confirmado con `psql -X -v ON_ERROR_STOP=1 -f sql/021_create_raw_tables.sql`.
   El archivo tiene BEGIN/COMMIT y crea exclusivamente las ocho tablas faltantes
   con columnas TEXT, sin claves, índices, valores por defecto ni restricciones
   que alteren la conservación de filas. No modifica `raw.orders`. Si una tabla
   ya existe, falla y revierte toda la migración; no oculta diferencias con
   `CREATE TABLE IF NOT EXISTS`. No es una migración para repetir a ciegas.
5. Verificar con consultas de solo lectura que existen las nueve tablas y que
   `raw.orders` conserva sus ocho columnas TEXT originales en el mismo orden.
   Usar para carga un usuario con USAGE en raw y SELECT/INSERT/TRUNCATE sobre los
   destinos previstos; no necesita CREATE ni permisos sobre otros esquemas.
6. Programar una ventana por el bloqueo exclusivo de TRUNCATE, configurar los
   `PG*` por un mecanismo seguro y comenzar con un dataset nombrado y `--replace`.
   Revisar conteo confirmado y datos representativos; después autorizar `all` o

7. Ante un fallo, la tabla actual vuelve a su estado anterior por rollback;
   revisar los commits previos antes de reintentar. Para deshacer una carga que
   ya hizo commit, restaurar el respaldo o recargar la versión fuente aprobada.

## Riesgos y límites conocidos

- El bloqueo exclusivo dura hasta commit/rollback y puede esperar a otros lectores
  o escritores. No se configura un tiempo máximo de espera; planificar la ventana.
- Los CSV deben permanecer estables entre validación y COPY. No hay snapshots de
  archivos ni verificación criptográfica adicional durante la carga.
- El control de estructura valida nombres, orden y tipo TEXT. No inspecciona
  triggers, políticas, reglas o restricciones añadidas externamente; revisarlos
  durante el despliegue. Las tablas del DDL no incluyen estos mecanismos.
- El conteo final comprueba cantidad, no igualdad criptográfica de valores ni
  orden de filas. PostgreSQL no garantiza orden sin `ORDER BY`.
- La operación `all` puede dejar un avance parcial entre datasets; no hay rollback
  global ni reintentos automáticos. No se usa `TRUNCATE CASCADE`.
- Se conserva el límite de tamaño de campo del lector CSV de Python de RS-020;
  campos que lo superen se rechazan antes de conectar. Las pruebas de streaming
  permanecen por debajo del límite.
- El DDL y la integración generalizada aún no se han validado contra una base
  real. En esta implementación no se conectó a PostgreSQL, no se ejecutó DDL ni
  se modificaron registros, `data/raw` o `compose.yaml`. No se hizo commit ni push.
