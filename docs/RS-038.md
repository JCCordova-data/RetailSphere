# RS-038: Implement Repeat Customer Analytics

RS-038 implements RF-003: identify repeat buyers and measure their share of
customers with completed purchases. The MVP adds `analytics.repeat_customers`
at buyer grain, allowing Power BI to list individual buyers and aggregate
purchase and repeat-customer indicators without repeating global totals.

## Objective and scope

Implement repeat purchase analysis through the existing RAW -> CLEAN ->
ANALYTICS architecture. Repository inspection covered the project README,
RS-031/032/036/037 documentation, all existing models and schema definitions,
macros, singular tests, and saved dbt artifacts. PostgreSQL metadata confirmed
the actual relations and types. There were no existing source declarations;
the reviews source added for RS-039 does not change existing dependencies.

The business rules below are implementation assumptions made under the
owner's authorization to complete the MVP autonomously. They remain subject
to manual Code Review. No existing model SQL, RAW data, ingestion code,
configuration, or infrastructure was changed. The original implementation and
read-only SQL validation did not run dbt or Git commands. The owner subsequently
completed manual dbt validation, as recorded below.

## Architecture and dependencies

```text
raw.orders    -> clean.orders    --+
raw.customers -> clean.customers --+-> analytics.repeat_customers
```

[`repeat_customers.sql`](../dbt/retailsphere/models/analytics/repeat_customers.sql)
uses `ref('orders')` and `ref('customers')`. The current CLEAN views preserve
customer identities and safely type order timestamps. No item, payment, or
review join is necessary. This avoids multiplying purchases by their items,
payments, or reviews.

The existing analytics configuration materializes the model as a view. The
existing schema macro places it in literal `analytics`; CLEAN continues to
use the profile's existing `clean` schema. No materialization or schema
configuration was added or changed.

## Business rules and aggregation grain

- Use the original `customer_unique_id` as the distinct buyer key.
- Include only `order_status = 'delivered'`, across all available history.
  Eligibility does not depend on item presence, payment totals, or timestamps.
- Count distinct qualifying `order_id` values per buyer. One order counts
  once even if an identical joined row is repeated.
- Exactly one completed purchase means one-time buyer; at least two means
  repeat buyer. Buyers without a delivered purchase do not receive a row.
- The repeat-rate population is identifiable buyers with at least one
  delivered purchase, including both one-time and repeat buyers. The 96,096
  buyers in the full customer table are not the denominator.
- Exclude unmatched customer records and NULL/blank customer, buyer, or
  order IDs. Do not merge unidentified purchases into a synthetic buyer or
  substitute `customer_id`. A dedicated test reports these exclusions as
  quality failures requiring investigation.
- `BTRIM` is used only to detect blank keys. Original nonblank identifiers
  remain unchanged; no whitespace normalization or identity repair occurs.

The grain is one row per identifiable purchasing buyer, rather than a global
summary or a customer/order pair. Counts can therefore be aggregated directly
in Power BI. Empty eligible input produces zero rows; aggregate measures
return zero counts and a NULL/BLANK rate with a zero denominator.

The model relies on CLEAN's unique customer and order IDs. `COUNT(DISTINCT)`
prevents repeated rows from inflating one buyer's purchase count; it cannot
resolve a customer ID incorrectly mapped to different buyer identities.

## SQL implementation and columns

The `customer_purchases` CTE joins orders to customers on `customer_id`, filters
eligible purchases and identifiable buyers, then groups by `customer_unique_id`.
The final projection computes `is_repeat_customer` from the purchase count.
No additional intermediate model or stored percentage is needed.

| Column | PostgreSQL type | Definition |
| --- | --- | --- |
| `customer_unique_id` | TEXT | Unique non-NULL, nonblank buyer key, preserved from CLEAN. |
| `completed_purchases` | BIGINT | `COUNT(DISTINCT orders.order_id)` for the buyer's delivered purchases; at least one. |
| `is_repeat_customer` | BOOLEAN | `completed_purchases >= 2`; FALSE means exactly one purchase. |

## KPI formulas and Power BI usage

Use buyer rows for customer KPIs; do not sum repeated customer-level totals
after joining to orders. The exact SQL formulas are:

| KPI | Formula over `analytics.repeat_customers` |
| --- | --- |
| Total purchasing customers | `COUNT(*)` |
| One-time customers | `COUNT(*) FILTER (WHERE NOT is_repeat_customer)` |
| Repeat customers | `COUNT(*) FILTER (WHERE is_repeat_customer)` |
| Completed purchases | `COALESCE(SUM(completed_purchases), 0)` |
| Repeat customer rate (%) | `100::NUMERIC * COUNT(*) FILTER (WHERE is_repeat_customer) / NULLIF(COUNT(*), 0)` |

Recommended DAX measures, using imported table name `repeat_customers`:

```dax
Total Purchasing Customers =
    COALESCE(COUNTROWS('repeat_customers'), 0)

One-Time Customers =
    CALCULATE(
        [Total Purchasing Customers],
        KEEPFILTERS('repeat_customers'[is_repeat_customer] = FALSE())
    )

Repeat Customers =
    CALCULATE(
        [Total Purchasing Customers],
        KEEPFILTERS('repeat_customers'[is_repeat_customer] = TRUE())
    )

Completed Purchases =
    COALESCE(SUM('repeat_customers'[completed_purchases]), 0)

Repeat Customer Rate =
    DIVIDE([Repeat Customers], [Total Purchasing Customers])
```

Format the rate as Percentage; DAX returns a 0-1 fraction, so do not multiply
it by 100 as well. Retain full precision until display. `KEEPFILTERS` respects
the current visual/filter context. A card filtered to repeat buyers alone has
a 100% within-filter rate; use the full purchasing population for the headline
rate.

Buyer IDs are categorical fields with summarization disabled. Use
`completed_purchases` and `is_repeat_customer` in a buyer detail table and the
measures in cards. Repeat status describes the entire available history.
An order-date slicer cannot recalculate period-specific repeat status from
this view. A later cohort/period requirement needs order-grain logic.

Avoid a many-to-many join from this view to `clean.customers`, where the buyer
ID repeats. If future reporting requires identity relationships, treat this
view's buyer key as the one side and use the existing customer/order mapping
deliberately. Do not assign one arbitrary customer address to a buyer who has
multiple customer records. Power BI changes are recommendations only and
were not implemented or tested.

The RAW baseline is intentional: these tests also expose upstream identity or
status drift. It references existing `raw.orders` and `raw.customers` like
earlier project tests, without adding unnecessary source declarations.
Reconciliations use `IS DISTINCT FROM`; empty sums are coalesced to zero and
rates use `NULLIF`. No dataset totals are hardcoded in tests or models.
The percentage checks validate SQL measure inputs and formulas; they cannot
validate a Power BI measure that has not been implemented.

This read-only query reproduces the independent source baseline:

```sql
WITH buyer_purchases AS (
    SELECT
        c.customer_unique_id,
        COUNT(DISTINCT o.order_id) AS purchases
    FROM clean.orders AS o
    JOIN clean.customers AS c ON o.customer_id = c.customer_id
    WHERE o.order_status = 'delivered'
      AND NULLIF(BTRIM(o.order_id), '') IS NOT NULL
      AND NULLIF(BTRIM(o.customer_id), '') IS NOT NULL
      AND NULLIF(BTRIM(c.customer_unique_id), '') IS NOT NULL
    GROUP BY c.customer_unique_id
)
SELECT
    COUNT(*) AS purchasing_customers,
    COUNT(*) FILTER (WHERE purchases = 1) AS one_time_customers,
    COUNT(*) FILTER (WHERE purchases >= 2) AS repeat_customers,
    COALESCE(SUM(purchases), 0) AS completed_purchases,
    100::NUMERIC * COUNT(*) FILTER (WHERE purchases >= 2)
        / NULLIF(COUNT(*), 0) AS repeat_customer_rate_pct
FROM buyer_purchases;
```

## Limitations and remaining risks

- This is an all-history repeat purchase share, not time-based retention,
  churn, frequency within a period, or cohort retention. Dataset boundaries
  can hide purchases before or after the observed history.
- Delivered status is the completed-purchase proxy. Refunds and returns are
  not available in the modeled contract and are not inferred from reviews.
- Buyer identity follows the supplied `customer_unique_id`; cross-account
  identity resolution is outside scope.
- Missing or unmatched identities are excluded and reported by tests. A
  published KPI should follow review of those failures if future data changes.
- Existing CLEAN uniqueness and relationship contracts remain prerequisites;
  this ticket does not repair upstream records.
- Views reflect current source data, so benchmarks can change. The owner has
  completed full dbt integration validation; Power BI implementation and
  refresh validation remain pending.
